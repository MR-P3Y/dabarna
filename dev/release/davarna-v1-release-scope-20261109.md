# دبرنای طوفان — محدوده نسخه 1.0 و وضعیت انتشار

تاریخ تنظیم: 2026-11-09

## تصمیم نسخه 1.0
نسخه 1.0 بر **اجرای پایدار بازی موجود با کنترل ادمین** متمرکز است، نه افزودن قابلیت جدید. این شاخه از `bc91e23f55d0187820b69be78737486da4b32e41` شروع شده و مجموعه اصلاحات قوانین/اعلان‌های PR #33 و تأیید ارسال/بازیابی PR #34 را یکجا دارد. هدف پایه مقایسه: `release/combined-forum-mini-candidate-20261107`.

## در محدوده RC
- قوانین ذخیره‌شده هر بازی: `LINE` (۱۵ عدد؛ تورنا ۳ عدد یک ردیف؛ خطی ۵ عدد یک ردیف)، `FULL_CARD` (۱۵ عدد بدون تورنا)، `LEGACY` (۴×۵، ۲۰ عدد تاریخی).
- اعلان لابی، شروع واقعی، شماره‌های زنده، نتایج و پنل مدیریت با برچسب قانون هر بازی.
- `USER_TOPIC_GAME_START_ID` **اختیاری**؛ در Production تا شناسایی واقعی شناسه، unset باقی بماند و مسیر اعلان موجود حفظ شود.
- تأیید ارسال تلگرام **به‌ازای هر مقصد** با بازپخش تلاش ناموفق پس از ری‌استارت و فایل وضعیت قابل‌بازیابی.
- نگهداری محافظه‌کارانه اجرای دستی موجود؛ **هیچ تغییر تازه‌ای در فلگ‌های Autopilot، AUTO DRAW یا اجرای زمان‌بندی‌شده** در این RC.
- عدم تغییر فایل‌ها/آدرس‌های رمزارز، کیف پول، جایزه، بازپرداخت، schema و تنظیمات مالی با این RC.

- زمان‌بندی واقعی «۵ دقیقه قبل از شروع» در Issue #27؛ شروع وابسته به حداقل دو بازیکن متمایز است و تا زمان قطعی، نباید countdown ساختگی اعلام شود.

- PR #33: ۶/۶ آزمون قرارداد قوانین/تاپیک در NODE2 موفق.
- PR #34: ۱۵/۱۵ آزمون وضعیت ارسال/restart + ۶/۶ همان قراردادها موفق؛ در مجموع ۲۱/۲۱.

- هیچ CI status/workflow برای commitهای تست‌شده ثبت نشده است.
- **تست واقعی تلگرام انجام نشده**؛ جست‌وجوی محدود NODE2 محیط Staging مستقلی پیدا نکرد و کاربر ساخت محیط آزمایشی جدید را لازم ندانست.
- «ارسال دقیقاً یک‌بار» از سوی تلگرام قابل تضمین نیست؛ نتیجه فعلی تلاش قابل‌بازیابی با احتمال تکرار بعد از قبول پیام و قبل از ACK است.
- جریان کامل خرید تا تسویه و صحت مالی روی Release Candidate در دیتابیس جداگانه **دوباره تست نشده**؛ صحت Production یا مناسب‌بودن RC برای پرداخت واقعی هنوز قابل ادعا نیست.

## تنها گام فنی باقی‌مانده برای بررسی اولیه
فقط یک بار اسکریپت خواندنی `dev/release/davarna-v1-rc-readonly-gate-20261109.sh` روی NODE2 اجرا شود. این تست روی نسخه pin شده آفلاین اجرا می‌شود؛ از Docker فقط وضعیت خوانده می‌شود و هیچ Deploy یا Migration انجام نمی‌شود. اگر FAIL بود فقط همان نقص مشخص اصلاح شود، نه شروع کار جدید.

## انتشار — نیازمند تأیید جداگانه
1. قبل از اقدام، مشخصات واقعی نسخه فعلی Production، health، image و backup فایل وضعیت اعلان و پایگاه داده را تأیید کنید؛ بدون چاپ secret.
2. از Production یک نسخه بازگشت قابل اتکا تهیه و صحت آن را تأیید کنید؛ عملیات مالی و flagها نباید در rollout تغییر کنند.
3. کاربر باید *به‌صورت مجزا* ادغام/انتشار نسخه موردنظر روی Production را تأیید کند. شروع کار روی RC به معنی اجازه استقرار نیست.
4. هر Deployment باید با rollback و کنترل خطای notifier، صحت API و ماندگاری ACK پایش شود. به‌دلیل نبود تست واقعی Staging، ریسک انتشار عملیاتی تلگرام صریحاً پذیرفته یا انتشار متوقف شود.

**وضعیت فعلی: کاندیدای انتشار در حال آماده‌سازی؛ نه نسخه 1.0 منتشرشده.**
