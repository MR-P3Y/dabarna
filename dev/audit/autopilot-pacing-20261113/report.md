## آزمون‌های اجراشده برای بخش زمان‌بندی

- Backend: **۱۹۸ موفق + ۸۰ subtest**؛ ۲ opt-in در اجرای عمومی skip شدند (fresh MySQL migration و MySQL dashboard). هیچ‌کدام به‌عنوان PASS همین اجرا حساب نشده‌اند. ۳۳ هشدار deprecation موجود ثبت شده است.
- Bot: **۶۵ موفق + ۱۲ subtest**.
- JavaScript: **۱۱ مجموعه موفق**، شامل V1.3/RBAC، قوانین، رسید و اعلان، countdown و timeline.
- MySQL واقعی ولی کاملاً محلی: **۴ چرخه موفق**؛ LINE/8s و FULL_CARD/2s،3s،4s. خرید و کیف پول آزمایشی، حداقل دو بازیکن، مهلت آمادگی، شروع، draw، برد، مجموع جایزه/کمیسیون، عدم پرداخت مجدد و ساخت دور بعد بررسی شد. تراکنش بیرونی هر تست rollback می‌شود. Redis mock است و drawها بدون خواب چندثانیه‌ای فراخوانی می‌شوند؛ deadline اولین عدد و فاصله ذخیره‌شده بررسی شده، این آزمون benchmark زمان‌بندی زیر بار نیست.
- Migration: نصب تا `20261113_0013`، upgrade تکراری، downgrade به `0012` و upgrade مجدد موفق، صرفاً در دیتابیس تست `davarna_tambola_v2_test_20261104` روی شبکه Docker داخلی.
- Chrome: فایل‌های واقعی برنامه با APIهای mock، موبایل 390×844 و دسکتاپ1440×960؛ pending، stale، ادغام pollهای هم‌زمان، لغو countdown قدیمی، تنظیم مهلت توسط ادمین و گزینه‌های وابسته به قانون موفق. **صفر درخواست نوشتن و صفر پیام به Telegram**. تصاویر و `result.json` پیوست‌اند.
- Python compileall، Node syntax و git diff --check موفق.

شکست‌های رفع‌شده: آماده‌نبودن TCP و authentication در MySQL محلی با انتظار اتصال واقعی اصلاح شد؛ migration ابتدا به محدودیت Trigger در سرور آزمایشی برخورد کرد و مجوز همان سرور Docker محلی اصلاح شد. fixtureهای قدیمی countdown اکنون readiness ذخیره‌شده دارند. تست مرورگر ابتدا به فرم پنهان زیر پوسته احراز هویت mock رسید؛ نمایش پوسته آزمایشی پیش از تعامل اصلاح شد. assertionها حذف یا تضعیف نشدند.

## قرارداد اجرایی و محدودیت‌ها

فقط Worker موجود بازی را می‌سازد و شروع می‌کند. فرانت‌اند GET می‌خواند و زمان باقی‌مانده را نمایش می‌دهد؛ رسیدن به صفر هیچ command ایجاد نمی‌کند. poll دوثانیه‌ای فقط در تب بازی فعال و صفحه قابل مشاهده است. تأخیر شبکه، tick یک‌ثانیه‌ای شماره‌خوان و بار سرور می‌تواند اجرای واقعی را عقب بیندازد؛ UI منتظر تأیید می‌ماند. زمان قطعی پایان بازی اعلام نمی‌شود، چون به اعداد و نتیجه بازی وابسته است.

تغییر تنظیم countdown، تایمر آغازشده را جابه‌جا نمی‌کند. تغییر سرعت روی شماره‌خوان قفل‌شده بازی RUNNING مجاز نیست. مهلت و سرعت بازی بعدی قابل تنظیم‌اند. نقش‌ها، کمیسیون، خرید و محاسبه جایزه دست‌نخورده‌اند.

## Deploy و Rollback پیشنهادی؛ اجرا نشده

1. تأیید جداگانه Merge/انتشار لازم است. ابتدا SHA دقیق، imageهای فعلی، schema0012، عدم بازی RUNNING و تنظیمات موجود مجدداً فقط‌خواندنی تأیید شوند. نبود پنجره امن به معنی تعویق rollout است؛ هیچ بازی را برای ایجاد پنجره متوقف نکنید.
2. پشتیبان خصوصی دیتابیس و Compose، imageهای immutable جدید Backend/Bot، و smoke همان imageها آماده شوند. تنظیمات مالی و مقادیر Autopilot فعلی حفظ شوند. اسکریپت قدیمی image-only برای این migration کافی نیست.
3. اجرای migration0013 فقط در مسیر DBA تأییدشده، همراه کنترل مجوز Trigger و نسخه دقیق متن guard. MySQL DDL تراکنشی نیست؛ شکست میان DROP/CREATE trigger نیازمند بازیابی guard پیش از ادامه سرویس است. در پنجره migration باید نویسندگان برنامه طبق برنامه تأییدشده متوقف باشند؛ این گزارش چنین عملیاتی را اجرا یا مجاز نمی‌کند.
4. Backend/Bot از همان SHA، سپس health، RBAC، asset hash، تنظیمات، deadline و مشاهده چرخه طبیعی بازی؛ به کاربران واقعی پیام تست ارسال نشود.
5. بازگشت برنامه به imageهای قبلی در صورت خطای health، با حفظ ستون افزوده‌شده. اگر بازی ۲/۳/۴ثانیه‌ای ثبت شده باشد، **downgrade schema ممنوع است** و خود migration آن را رد می‌کند. هیچ سابقه‌ای حذف نشود. بازگشت به برنامه قدیمی که سرعت سریع را نمی‌پذیرد، تا تعیین تکلیف امن بازی‌های سریع/تنظیمات جدید کامل نیست؛ rollback صرفاً تعویض image تلقی نشود.
