# مدیریت آدرس TON و USDT-TRC20 — بازبینی مستقل ۱۳ نوامبر ۲۰۲۶

**به‌روزرسانی:** [ادامهٔ بررسی سابقه و مقصدهای قبلی](history-followup-20261113.md) مرجع وضعیت جدید است: محدودیت کلیِ هر سابقه، در کد نامزد با تطبیق تازه و قفل‌شده و حفظ پایش مقصد قبلی جایگزین شده است. نتایج جدید ۲۸۹ تست Backend، ۷۳ Bot و ۹ MySQL هستند. متن پایین سابقهٔ بازبینی قبلی را حفظ می‌کند. نامزد همچنان منتشر نشده و تأیید مستقل مالی لازم است.

**Draft، Merge نشده، منتشر نشده؛ هیچ مقصد واقعی یا تنظیم مالی تغییر نکرده است.** این نامزد روی نسخه فعلی Superadmin V1.3 و [PR غیرمالی #52](https://github.com/MR-P3Y/dabarna/pull/52) قرار دارد. PR #49 با Head `e421157c003c6f76a3bba6e600d7c5e9afb4b596` روی V1.2 بود؛ کد مالی لازم انتخابی منتقل شد و UI قدیمی، migrationهای قبلی و اسکریپت‌های استقرار آن منتقل نشدند.

## تغییرات قابل بازبینی

- افزودن اولیه، درخواست تغییر، بررسی آمادگی، تأیید و لغو در Mini App و ربات خصوصی؛ API ربات همان منطق Backend را استفاده می‌کند. نقش معمولی، مالی و اپراتور بازی مجاز نیستند. در نبود شناسه مالک، API جدید مدیریت آدرس بسته می‌ماند.
- ثبت نسخه مقصد در AppSetting، قفل MySQL، مقایسه آدرس/نسخه، audit و عدم روشن‌شدن خودکار پرداخت. مقصد فاکتورهای قبلی تغییر داده نمی‌شود.
- تأیید ربات به آدرس، نسخه، آدرس قبلی و زمان همان درخواست نمایش‌داده‌شده متصل شد. اگر در فاصله انتظار درخواست عوض شود، تأیید قدیمی اجرا نمی‌شود.
- لغو درخواست با قفل رکورد و بررسی آدرس/زمان ایجاد؛ درخواست لغوشده حفظ می‌شود و کلیک قدیمی نمی‌تواند درخواست جایگزین را لغو کند. تاریخچه audit محفوظ است.
- اعتبارسنجی checksum TON/TRON؛ آدرس TON تست‌نت، flag و workchain نامعتبر رد می‌شوند. raw/bounceable/non-bounceable مربوط به یک حساب به‌عنوان تغییر مقصد متفاوت پذیرفته نمی‌شوند. قالب‌های معتبر یک حساب در تطبیق پاسخ provider نیز معادل‌اند؛ رشته مقصد فاکتور تاریخی بازنویسی نمی‌شود. مرجع قالب: [TEP-2 رسمی TON](https://github.com/ton-blockchain/TEPs/blob/master/text/0002-address.md).
- تطبیق مقصد واقعی تراکنش با فاکتور، memo اجباری TON در حالت نسخه‌دار، اسکن چند مقصد و pagination با توقف در خطا، ثبت مشاهده و صف بررسی بدون پرداخت خودکار موارد دیررس.
- شکست بررسی آمادگی در UI به پیام قابل‌فهم و آزادشدن دکمه منجر می‌شود؛ هیچ درخواست فعال‌سازی در آن حالت ارسال نمی‌شود.

این شمارش‌ها همپوشانی دارند و نباید با نامزد غیرمالی جمع زده شوند. چهار skip مجموعه عمومی شامل تست‌های opt-in MySQL هستند که جداگانه در شبکه Docker داخلی اجرا شدند. نام میزبان/دیتابیس سخت‌گیرانه و dummy credential در gateها از اجرای اتفاقی روی دیتابیس واقعی جلوگیری می‌کند. schema آزمون مقصد `davarna_wallet_rotation_test` و host آن `davarna-wallet-mysql` است؛ هیچ volume تولید در آن mount نشده است.

شکست‌های اصلاح‌شده: fixtureهای قدیمی تطبیق فاقد مقصد فاکتور بودند؛ مقصد معتبر fixture افزوده شد و assertion حفظ شد. واردکردن schema/توابع مشترک Mini در Bot هنگام انتقال انتخابی ناقص بود و تکمیل شد. اجرای اولیه MySQL به مسیر receipt فقط‌خواندنی و سپس cache احراز هویت نیاز داشت؛ با مسیر موقت و اتصال اولیه local fixture اصلاح شد. migration تست به مجوز ساخت trigger نیاز داشت که فقط روی MySQL موقت داده شد. هیچ assertion حذف، تست خاموش یا خطای ناموفق به‌عنوان PASS معرفی نشد.

## محدودیت واقعی انتشار

فعال‌سازی عملیاتی در این نسخه **هر فاکتور تاریخی/باز روی مقصد قبلی را مسدود می‌کند**. پاک‌کردن فاکتور، ledger یا موجودی برای عبور از این قید ممنوع است. در نتیجه این نامزد به‌تنهایی ادعای تکمیل چرخش آزاد آدرس روی حساب دارای سابقه ندارد. قابلیت مدیریت از محیط عملیاتی به‌صورت پیش‌فرض خاموش است؛ هیچ gate مالی در این مأموریت روشن نشده است.

برخی سخت‌گیری‌های تطبیق مقصد و parser/provider در این شاخه حتی با gate چرخش خاموش، تفاوت رفتاری دارند؛ پس این PR «صرفاً UI» نیست و باید **جداگانه بازبینی و تأیید مالی** شود. آن‌ها عمداً در PR غیرمالی قرار نگرفته‌اند. پاسخ واقعی providerهای TON/TRON، rate-limit طولانی‌مدت و بازیابی پس از جابه‌جایی واقعی مقصد با پول واقعی تست نشده‌اند. موفقیت دیتابیس آزمایشی مجوز فعال‌سازی روی Production نیست.

نیاز باقی‌مانده پیش از انتشار مالی: تصمیم روشن درباره مقصد دارای سابقه، بررسی قابل حسابرسی فاکتورهای قدیمی بدون حذف آن‌ها، پذیرش پوشش اسکن و reconciliation، بررسی provider واقعی با دسترسی فقط‌خواندنی و تأیید مشخص مالک برای هر تغییر مقصد. از طرح clean-launch در متن PR قدیمی، مجوز تغییر دیتابیس Production فعلی استنباط نمی‌شود.

Rollback مالی با برگشت ساده env gate مجاز نیست: اگر روزی آدرس نسخه‌دار واقعاً فعال شد، خاموش‌کردن gate ممکن است برنامه را به مقصد قدیمی env برگرداند. باید صدور فاکتور تحت برنامه تأییدشده متوقف، مقصدهای روی فاکتورهای موجود حفظ، اسکن آدرس‌های قدیم/جدید ادامه و نسخه مقصد تحت همان قفل و audit بازیابی شود؛ هیچ ledger یا فاکتور تاریخی بازنویسی نشود. در این مرحله هیچ activation واقعی وجود نداشته که rollback آن لازم باشد.
