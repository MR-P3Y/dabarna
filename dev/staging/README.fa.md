# راهنمای آماده‌سازی Staging مستقل دبرنا

## تصمیم فعلی

پنج موج UI/UX از تست‌های ایزوله عبور کرده‌اند، اما جریان واقعی پرداخت و اعلان تلگرام هنوز در یک محیط Staging جدا آزمایش نشده است. **اسکریپت این پوشه فقط پیش‌پرواز خواندنی است** و هیچ سرویس جدیدی را اجرا نمی‌کند.

## خطرهای کشف‌شده در Compose اصلی

- `docker-compose.yml` دارای `container_name: davarna-*` ثابت است. `docker compose -p ...` به‌تنهایی برای جداسازی کافی نیست.
- متغیرهای `BACKEND_ENV_FILE` و `BOT_ENV_FILE` با پیش‌فرض فایل‌های Production مقداردهی می‌شوند. از آن‌ها برای Staging استفاده نکنید.
- Backend در Dockerfile هنگام شروع `alembic upgrade head` و seed اجرا می‌کند. کوچک‌ترین اشتباه در `DATABASE_URL` می‌تواند دیتابیس اشتباه را تغییر دهد.
- `GAME_AUTO_DRAW_ENABLED` در config به‌صورت پیش‌فرض فعال است؛ برای Staging باید صریحاً `false` شود. همچنین `GAME_AUTOPILOT_RUNTIME_ENABLED=false`، `CRYPTO_PAYMENTS_ENABLED=false` و `CRYPTO_AUTO_CONFIRM_ENABLED=false` ضروری‌اند.
- احراز هویت Mini App واقعی وابسته به `TELEGRAM_BOT_TOKEN` است. برای Staging نیاز به Bot **مستقل و آزمایشی** و دامنه HTTPS جداگانه داریم؛ توکن ربات اصلی، کیف پول/کارت بانکی اصلی یا شناسه گروه اصلی نباید به Staging منتقل شود.
- استفاده از HTTP localhost فقط برای پیش‌نمایش/Smoke test در مرورگر است، نه آزمون کامل در Telegram WebApp.
- برای اجرای MySQL + Redis + Backend + فرایند build، RAM و فضای خالی کافی لازم است. وجود Swap بالا یا حافظه محدود روی NODE2 ممکن است مانع اجرا باشد.

## مرحله ۱ — پیش‌پرواز بدون تغییر سیستم

روی NODE2:

```bash
(
  set -Eeuo pipefail
  cd /opt/davarna-v2
  git pull --ff-only origin feature/ui-ux-refresh-tambola-v2-20261106
  bash dev/staging/preflight.sh
)
```

این اسکریپت به فایل‌های secret و `.env.prod` دست نمی‌زند. فقط شاخه کد، مقدار RAM آزاد و Swap، فضای دیسک، نام/وضعیت کانتینرها و آزاد بودن پورت آزمایشی `18190` را گزارش می‌کند. اگر مانع ظرفیت وجود داشته باشد، با وضعیت خروج ۲ متوقف می‌شود.

**عمداً هیچ دستور `docker compose up`، `docker compose down`، `alembic` یا `docker build` در این مرحله وجود ندارد.**

## مرحله ۲ — پس از تأیید ظرفیت و محیط آزمایشی

1. ترجیحاً یک VPS جدا با دامنه HTTPS مستقل انتخاب شود. در صورت انتخاب NODE2، ظرفیت و ریسک اختلال باید ابتدا تأیید گردد.
2. Compose اختصاصی با پروژه، شبکه، دیتابیس، Redis، Volume و پورت مستقل ساخته شود؛ نام ثابت کانتینرهای Production تکرار نشوند.
3. هیچ اطلاعات واقعی مالی، توکن، آدرس رمزارز، رسید، اطلاعات کاربر یا ادمین Production کپی نشود. اگر دیتای نمونه لازم شد، داده ساختگی seed شود.
4. Workers کریپتو، شماره‌خوان خودکار و Autopilot پیش از اولین اجرا با متغیرهای صریح غیرفعال شوند؛ کاربر واقعی و گروه اصلی نباید پیام آزمایشی دریافت کنند.
5. ابتدا فقط سلامت Backend و رابط موبایل بررسی شود. سپس با Bot آزمایشی در HTTPS، ورود، نمایش بازی، کارت، و اعلان‌ها آزمایش شوند.
6. سناریوهای تراکنش/برد/لغو/بازپرداخت صرفاً با پول و داده ساختگی بررسی شوند. برای انتشار اصلی بازبینی جداگانه لازم است.

- ⏳ آزمون دستی Telegram Mini App با Bot مستقل
- ⛔ هنوز مجوز انتشار روی Production صادر نشده است
